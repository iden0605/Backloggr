## What It Is

**backloggr** (name confirmed 2026-07-07; backloggr.com) — a Windows-first desktop app (Tauri + React) for tracking a personal game **library** (owned games + per-game playtime stats, not a completion queue), auto-logging playtime, getting AI-driven "what to play next" suggestions from **Shelby** (the named AI chatbot — all user-facing chat copy says Shelby, not "AI"), and saving gameplay clips via a hotkey. Single-user, local-first.

## Stack

- **Framework:** Tauri v2 (Rust backend + WebView frontend)
- **Frontend:** React 18 + Vite + TypeScript, Tailwind CSS v3 (via PostCSS, not the v4 Vite plugin), Zustand (state), React Router (`HashRouter`, safe under Tauri's asset protocol), Recharts (Dashboard charts)
- **Backend (Rust):** `rusqlite` (bundled SQLite), `sysinfo` (process polling), `reqwest`/`tokio` (HTTP/async), `tauri-plugin-global-shortcut`, `tauri-plugin-shell`, `tauri-plugin-sql`, `tauri-plugin-single-instance` (prevents a second app copy from stacking a duplicate capture process/hotkey handler; its callback re-shows the possibly-hidden-to-tray window), `tauri-plugin-autostart` (launch-on-startup — LaunchAgent/registry, launches pass `--hidden` to boot straight to the tray), tray icon via tauri's built-in `tray-icon` feature (`tray.rs`), `windows` crate (Windows-only, target-gated — window-title resolution for scoped capture), macOS-only target-gated: `core-graphics`/`core-foundation` (game-window bounds for the save-time clip crop) + `objc` (raw NSWindow level/collection-behavior calls for the overlay toast). `tauri-plugin-notification` is still registered but unused — clip feedback moved to the in-game overlay window (`overlay.rs`); the tauri crate carries the `macos-private-api` feature for that window's transparency
- **External services:** RAWG API (game metadata + per-game details, key bundled server-side in Rust), Cloudflare Worker (`proxy/`) proxying Groq's chat completions API (AI recommendation chat) — deployed to a `*.workers.dev` subdomain; the worker URL is a bundled Rust const in `commands.rs` (same pattern as the RAWG key), not user-configurable
- **Media:** `ffmpeg` for a continuous rolling-buffer capture and clip extraction — bundled as a Tauri sidecar on Windows installs (`tauri.windows.conf.json` `externalBin`, staged by release.yml from a pinned gyan.dev build; `clipper.rs::ffmpeg_path()` resolves it next to the exe, PATH fallback for dev/macOS). Audio: mic (system-default input on macOS, name-matched dshow device on Windows) plus game/system audio — on Windows via native WASAPI loopback of the default output device (`loopback.rs`, cpal, raw PCM piped into ffmpeg's stdin — zero setup; dshow loopback devices are fallback only), on macOS via an installed loopback device (BlackHole etc.); tracks amix'd. `src-tauri/resources/tabbed_out.png` (bundled via `bundle.resources`) is the pre-rendered mask card composited over tabbed-out spans; see `clipper.rs` in Key Files
- **Deployment:** `release.yml` builds `.msi`/`.nsis`/`.dmg` installers on `v*` git tags via `tauri-apps/tauri-action` into a DRAFT GitHub Release (review, then publish by hand); the Windows leg stages the ffmpeg sidecar before building. A separate `windows-check.yml` workflow runs `cargo check` on `windows-latest` for every push/PR to dev/main (with empty placeholder `dist/` + sidecar files to satisfy tauri-build), since Windows-only code (`#[cfg(target_os = "windows")]` in `clipper.rs`/`loopback.rs`) is otherwise never compiled during local macOS development
- **Dev environment:** developed on macOS, ships for Windows — Windows-only pieces (`gdigrab`/`dshow` capture, window-title resolution, registry-based launch-on-startup, `.msi` build) can't be exercised locally and are validated via `windows-check.yml` and, eventually, manual testing on real Windows hardware

| `src-tauri/src/clipper.rs` | Stage 6 + 13b — continuous rolling-buffer capture + clip save, matching how Medal/ShadowPlay actually work: ONE ffmpeg process per game session, never stopped or swapped for focus changes. `ensure_capture(app, exe_name)` — called by `tracker.rs` on every poll while a session is open — starts capture, acts as a crash watchdog, honors `restart_requested` (deliberate kill from the mic toggle → fresh start with buffer wipe, no audio-failure strike), and on Windows upgrades a desktop-fallback capture to window-scoped once the game's title resolves. Capture writes MPEG-TS segments (`-segment_wrap`, `SEGMENT_SECONDS`/`BUFFER_SEGMENTS` consts) into `<appdata>/clip_buffer/`. **Audio** (`capture_input_args` → `CaptureInputs{args, window_scoped, audio_maps}`): up to two inputs — mic (macOS avfoundation `default` keyword; Windows `dshow_mic_device` name-match, gated by the `mic_enabled` setting via `get_mic_enabled`/`set_mic_enabled` — the setter kills the live capture so it applies within one poll) and a system-audio loopback device when installed (`is_loopback_device_name`); two tracks are amix'd in `spawn_ffmpeg`, each upconverted to 48kHz stereo pre-mix, always with explicit `-map`s. Device indexes are parsed fresh per spawn (`avfoundation_devices`, section-aware) — NEVER hardcoded. **Focus/tab-out**: a 1-second sampler (`spawn_focus_sampler`, only when NOT window-scoped) logs `is_frontmost` checks (`lsappinfo` on macOS; `GetForegroundWindow` on Windows) into `FocusLog`; `save_clip` composites the bundled `tabbed_out.png` (via `scale2ref`+`overlay=enable='between(t,a,b)+...'` — an image overlay is per-frame free, unlike the `geq` gradient it replaced which tripled save time) over unfocused spans, falling back to flat-black `drawbox` if the resource is missing. **Buffer math** (`recent_segments`): per-segment spans from mtime DELTAS between consecutive files, selection stops at footage holes; file creation times are never used (recycled `-segment_wrap` files keep their original birth time and broke the math after one ring lap). A finished clip probing as zero-duration is deleted and errors instead of being cataloged. **Window crop (macOS)**: `save_clip` crops the output to the game window — `game_window_rect_points` (CGWindowListCopyWindowInfo by the game's pids, largest window, no TCC needed for bounds) mapped to capture pixels via `probe_dimensions` of a real segment against display point size (avfoundation captures native panel pixels; nothing else gives the right scale); fullscreen/off-main-display skip the crop. Self-healing: `reap_orphan_capture` (startup + every fresh spawn) kills a leftover ffmpeg via `capture.pid`. `get_clips`/`delete_clip`/`get_clip_seconds`/`set_clip_seconds`/`get_mic_enabled`/`set_mic_enabled` round out the command surface. Save feedback goes through `overlay::toast` (saving → saved/failed), NOT OS notifications. ffmpeg resolves via `ffmpeg_path()` — bundled sidecar next to the exe when present (Windows installs), PATH otherwise (dev/macOS). |
| `src-tauri/src/loopback.rs` | Windows-only WASAPI loopback capture (task 16) — zero-setup game/system audio for clips, replacing the "install Stereo Mix / a virtual device" requirement (dshow loopback devices remain fallback when this can't open). `default_output_spec()` reads the default OUTPUT device's mix format via cpal (F32/I16 → `f32le`/`s16le`); `capture_input_args` adds a matching `-i pipe:0` raw-PCM input and `spawn_ffmpeg` pipes stdin to `loopback::start`. Design constraints baked in: the cpal callback runs on the audio-engine thread and must never block (bounded channel, `try_send`, drops on overflow); WASAPI loopback delivers NO packets while the machine is silent, so the writer thread paces total bytes against the wall clock and pads with silence to keep the audio track from drifting against the video. The thread is deliberately detached — its lifetime IS the pipe: capture ffmpeg killed → broken pipe → thread exits (no handle on `Capture`, no shutdown ordering). Compile-verified via windows-check; live behavior needs real Windows hardware. |

## Common Tasks

- **Add a Tauri command:** implement in `commands.rs`, register in `lib.rs`'s `invoke_handler![...]`, call from React via `@tauri-apps/api/core` `invoke()`.
- **Add a DB table/column:** update `SCHEMA` const in `db.rs`, add query logic in a command, expose it.
- **Add a new view/route:** create `src/components/<Area>/<Area>.tsx`, add a `<Route>` in `App.tsx`, add an entry to `navItems` in `Layout/TopNav.tsx`.
- **Add a dropdown:** use `shared/Select.tsx`, never a native `<select>` (user rule — OS default popups clash with the design).

## Conventions & Gotchas

- RAWG key must live as a Rust constant in `rawg.rs` — never expose it in the frontend bundle.
- Use `tauri-plugin-sql` only from the frontend for simple reads; use `rusqlite` directly in Rust (already wired via `DbState`) for anything with joins/aggregates.
- The tracker loop (Stage 3) must never block the main thread — use `tokio::spawn`.
- `sysinfo` returns `.exe`-suffixed names on Windows but extension-less names on Mac — `tracker.rs::normalize_exe_name` lowercases and strips `.exe` on both sides of the comparison.
- SQLite runs in WAL mode with `synchronous = NORMAL` (set in `db::init`) so the local DB survives app crashes/kills without the fsync cost of `FULL`; the file lives in the OS app-data dir, so it persists across restarts and app updates untouched.
- ffmpeg capture input differs by OS: `-f gdigrab` (Windows, window-scoped via `title=` when resolvable, else the whole desktop) vs `-f avfoundation` (Mac, always whole-screen — no window-capture mode exists for it) — branch in `clipper.rs::capture_input_args`. **Never kill/restart the capture process on a focus change** — that was tried (a live pause/black-generator-swap architecture) and reliably produced 0-byte segments, broken clip-length math, and inverted black-out masking under real tab-out testing. The working pattern: one continuous capture per session, non-game content excluded/masked at `save_clip` time instead.
- Cloudflare Worker must return CORS headers on every response or the Tauri WebView's fetch will fail.
- The Worker proxies to **Groq** (OpenAI-compatible chat completions), not Ollama — no self-hosted model to babysit; free-tier rate limits are generous enough for a single-user app. `GROQ_API_KEY` lives only as a Worker secret (`wrangler secret put`), never in the repo or frontend.
- The Worker's own URL is a hardcoded Rust const (`WORKER_URL` in `commands.rs`) — same pattern as the RAWG key, deliberately not user-configurable (an earlier version stored it in `settings` with a Settings UI field; reverted per user request to hide the detail from end users).
- Never let the model self-judge a multi-step AI flow's control flow from prose instructions alone — it doesn't reliably comply. The chat narrowing loop is deterministic in code: the model returns its real candidate pool + a possible clarifying question every round, but whether to show results vs. ask again is decided in `proxy/src/index.ts`'s `handleChat` from the pool's actual size, never from the model's own "I think I'm done" judgment. Apply the same pattern (model proposes data, code decides control flow) for any future multi-step AI feature. Extended 2026-07-06 to facts, not just flow: the model PROPOSES structured filters (release window, RAWG-taxonomy genres — never mood words like "cozy" — and platforms) and Rust ENFORCES them against each resolved game's real RAWG `released`/genre/platform values, dropping games whose facts can't be verified; a soft recency priority (`prioritize_recent`, 7 years) then reorders both chat and For You results. The model's own knowledge of release dates/genres is unreliable — never trust it where RAWG has the fact. The Groq model barely knows 2024+ releases — closed 2026-07-07 by `rawg::discover_recent` (date-range discovery, `-added` popularity ordering, genre-slug filtered, end date capped at today so unreleased games never surface): `chat_recommend` tops up short release-window results with it, and `fetch_suggestions` blends up to 2 top-genre new releases into every For You set.
- Chat history is never truncated/reset automatically between asks (it used to be, to stop an unrelated new ask from inheriting old context — but the user wants continued, deepening conversations instead); the explicit reset is the "New chat" button (2026-07-07), which starts a fresh `chat_conversations` row while the old conversation stays in the history sidebar. Conversations auto-save per exchange and the most recent one is restored once per app run; "Ask AI" from the find box after a restart deliberately starts a NEW conversation rather than splicing into last session's restored one. The model is explicitly told to focus on the *current* ask when the player has clearly moved topics (`TOPIC_FOCUS_NOTE` in the worker), rather than resetting history to prevent bleed. Results turns sent back as history must include the recommended titles ("(I recommended: ...)" — `historyForBackend` in DiscoverChat.tsx), or refinements like "something more modern than these" have no referent and the model regenerates the same set.
- A `transform` on any ancestor (including one only active on `:hover`, like a card's hover-lift) creates a new containing block for `position: fixed` descendants, so a `fixed inset-0` modal nested inside a hover-transformed card can render positioned relative to that card instead of the viewport. Render overlays/modals via `createPortal(..., document.body)` when the trigger element might have a transform.
- The color palette is locked: **Iron & Chalk** (`bg #151414`, chalk text `#EDE8E0`, rust accent `#B96A55`, full list in `tailwind.config.js`), chosen 2026-07-04 (replacing Aurora Teal) after three rounds of throwaway localhost HTML mockups — that mockup-server pattern remains the way to make palette/design decisions here. Two hard rules from the redesign: (1) **rust is a scarce "live marker"** — timers, live/pulse dots, active-nav underline, focus accents; primary buttons are chalk (`bg-text-hi text-bg`), NOT rust — the cover art is meant to be the loudest color on screen. One sanctioned exception (user-requested 2026-07-07): the Shelby chat page uses rust more freely — send button `bg-accent`, composer glow/focus ring, chip hovers, avatar, radial wash — scoped to that page only; don't "fix" it back to chalk, and don't take it as license to spread rust elsewhere; (2) the first round of palette candidates was rejected as "generic and AI-generated" (high-saturation single accent on near-black) — keep any future color work low-saturation/material-inspired.
- The layout is the **"Backdrop"**: no sidebar — a floating `TopNav` over content, and the Dashboard's top is a full-bleed hero of the featured game's own cover art (blurred/darkened, melting into `bg`) with a sharp poster + title + session timer at its base. Hero precedence when idle: currently playing → first backlog pick ("Up next") → most played ("Jump back in") → first-run welcome. Shell gives Dashboard a full-bleed wrapper, the chat page a viewport-height column (internal transcript scroll), and every other page a centered `max-w-5xl` column with `pt-24` clearing the nav.
- Page titles (and the TopNav logo) use the shared `.page-title` class (`src/index.css`, now bold Archivo) — upright, not italic. An italic display-serif treatment was tried in the Aurora Teal era and explicitly rejected by the user twice as "ugly"/"looks bad" — don't reintroduce italic display type for headings in this app. Section labels above shelves/groups use `.shelf-label` (small mono uppercase tracked).
- RAWG's search endpoint (`/games`) does not reliably return `description_raw`/`metacritic`/`developers`/`publishers`/`website` — those only come from the per-game detail endpoint (`/games/{id}`), which is why `get_game_details` is a separate on-demand call (triggered by `GameCard`'s expand) rather than folded into `search_games`.
- When asking Groq to recommend games, have it name specific titles it knows (an array of names), then resolve each individually via RAWG (`rawg::resolve_titles`) — a single keyword-search query against RAWG's title index surfaces shovelware clones (e.g. "farming simulation" → a wall of "Farming Simulator N" reskins) instead of genuinely varied results.
- Real-time updates (session start/end, clip saved) go Rust → frontend via `tauri::Emitter` + `listen()`, not polling. Treat these events as "refresh now" triggers only, not sources of truth on load — always fetch live/authoritative state (e.g. `get_currently_playing`) on mount too, since events emitted before a listener attaches are lost (no buffering), which matters especially for the tracker's startup reconciliation pass.
- SQLite's `CURRENT_TIMESTAMP` / `julianday()` are UTC but rendered without a timezone marker (`"YYYY-MM-DD HH:MM:SS"`). When parsing these in the frontend, append `"Z"` (after replacing the space with `"T"`) before `new Date(...)`, or JS silently treats them as local time.
- Auto-add-to-backlog is a path heuristic, not an authoritative library list: it only catches games that have actually been launched at least once, and only ones installed under a recognized storefront folder (`steamapps/common`, `Epic Games`, `GOG Games`, `Battle.net`, `Riot Games`). It cannot see games that have never been run, or that live outside those folder conventions — that gap is intentionally left for the future Steam-account sign-in import (Stage 10, plan task 17), not patched with more heuristics.
- RAWG calls inside `tracker.rs` must happen *before* acquiring `DbState`'s mutex, never while holding it — the connection is a plain `std::sync::Mutex`, and holding its guard across an `.await` blocks every other command trying to touch the DB for the duration of the network call.
- `foreign_keys = ON` is set in `db::init`, so deleting a row that other tables reference (e.g. a `games` row with `sessions`/`clips` rows pointing at it) fails with a foreign key constraint error unless dependents are deleted first — see `delete_game`'s transaction for the pattern to follow when adding new delete commands.
- A storefront's install-folder name often doesn't match RAWG's listed title verbatim (unspaced, abbreviated, etc.) — run it through `tracker::humanize_name` before searching RAWG rather than searching the raw name directly.
- Status is NOT a lifecycle (v2 library model, chosen with the user 2026-07-06): activity (playing now / played / never played) is always derived from `sessions` + the open session, and the only manual state is the two opt-in marks on the detail page — `completed` and `dropped` (rendered as "Not for me"; its covers dim in the grid). `backlog` just means "in the library"; `wishlist` is a separate tab, and launching a wishlisted game auto-moves it to the library. Don't reintroduce start-playing/move-to-backlog style transition buttons, and don't have the tracker write `playing` — that value is legacy, normalized away at db init.
- Tailwind is pinned to v3 (PostCSS-based) intentionally, per project plan — do not upgrade to v4/`@tailwindcss/vite` without discussion.
- The marketing website is a **separate repo**, not part of this one — this repo is app-only plus a future `proxy/` folder.
- Feature hotkeys/worker URLs/API keys are hardcoded Rust consts, not Settings fields, until a real Settings screen exists (Stage 8) — see `WORKER_URL` in `commands.rs` and `CLIP_HOTKEY` in `lib.rs`. Don't add a Settings UI field for one of these without discussion; the pattern is deliberate.
- ffmpeg is bundled as a sidecar only on Windows (`tauri.windows.conf.json` `externalBin`); dev builds and macOS resolve it from PATH via `clipper.rs::ffmpeg_path()`. Gotcha: tauri-build wants every `externalBin` file present at compile time even for `cargo check`, so `windows-check.yml` stages an empty placeholder at `src-tauri/binaries/ffmpeg-x86_64-pc-windows-msvc.exe` — a new workflow touching the Windows build needs the same step. Pin CI ffmpeg downloads to gyan.dev's versioned package URLs (permanent), never BtbN's "latest" assets (they rotate; and verify the URL with curl first — version guesses 404).
- **Never hardcode capture device indexes** — avfoundation/dshow device lists reorder as devices connect/disconnect (an iPhone inserts itself into the video list, headsets/BlackHole reorder audio). A hardcoded mic index silently became BlackHole (a silent loopback) in live testing, producing audio-less clips. Parse the device listing fresh at every capture spawn (`avfoundation_devices`/`dshow_audio_devices`), match by NAME, and prefer semantic selectors (avfoundation's `default` audio keyword) where they exist — but never trust the default blindly either: a loopback device can BE the system-default input (BlackHole did exactly this in live testing, silencing the mic track), so `capture_input_args` checks the default input's name (`macos_default_input_name`, via `system_profiler`) and falls back to a real mic by name when the default is a loopback (Windows' `dshow_mic_device` has the same guard).
- `-segment_wrap` recycles segment files in place, and a recycled file keeps its ORIGINAL creation timestamp (macOS) — any buffer math using file birth times breaks after one ring lap (~3 min), which produced unplayable zero-frame clips whose `-ss` seek ran past the real footage. Use mtime deltas between consecutive segments only (`recent_segments`), and treat a zero-duration output as a failed save.
- `amix` negotiates the LOWEST common audio format across its inputs — mixing a 16kHz-mono headset mic with 48kHz-stereo game audio degrades the game track to 16kHz mono. Upconvert every input (`aresample=48000,aformat=channel_layouts=stereo`) BEFORE the mix. Also: with multiple live capture inputs, always `-map` explicitly (ffmpeg's default best-stream selection is wrong here) and give each input `-thread_queue_size`.
- Per-pixel ffmpeg filter expressions (`geq`) are unusably slow at Retina resolutions (~tripled a 30s save). For masks/watermarks, pre-render a PNG and composite it (`scale2ref`+`overlay`) — per-frame cost is near zero, and it sidesteps `drawtext` (not compiled into Homebrew ffmpeg at all — a hard filtergraph error, not a degradation).
- OS notifications are the wrong surface for clip feedback and are NOT used: macOS suppresses banners whenever a fullscreen app is frontmost (posting succeeds, nothing shows — confirmed live). Use the overlay window (`overlay.rs`); the notification plugin stays registered but idle. Known open bug: the overlay itself still doesn't show over a fullscreen Steam game on macOS — see PLAN.md Open Questions before touching this area.
- Every Tauri window label must be listed in a capability file (`src-tauri/capabilities/default.json`) — a webview without a capability can't call ANY API, including `event.listen`, and fails silently. Also: tauri/tao reasserts its own NSWindow level during `show()`, so custom window levels must be re-applied after every show (see `overlay::elevate_above_fullscreen`), and transparent windows on macOS require the `macos-private-api` cargo feature + `macOSPrivateApi` conf flag pair.
- Game/system audio: Windows captures it natively via WASAPI loopback (`loopback.rs` — default output device, any headphones/speakers, zero setup; dshow Stereo Mix detection is only the fallback when the WASAPI stream can't open). On macOS it still requires a loopback device installed AND receiving audio: BlackHole plus a one-time user-created Multi-Output Device (speakers + BlackHole) selected as output — an unrouted loopback records silence, which is indistinguishable from "broken" in testing. WASAPI gotcha encoded in `loopback.rs`: loopback delivers no packets during silence, so the PCM writer must pad with wall-clock-paced silence or the clip's audio drifts against the video.
- A previous life of the app that dies without running its exit cleanup (crash, force-kill, or — constantly during development — `tauri dev`'s hard-kill on every rebuild) orphans the capture ffmpeg, which keeps recording indefinitely into a buffer a fresh instance will read from. `clipper::reap_orphan_capture` (called at startup and before every fresh capture spawn) kills it via a PID recorded in `capture.pid`, verifying the PID still names an `ffmpeg` process first (PIDs get reused). `tauri-plugin-single-instance` independently prevents two live copies of the app from both trying to own capture at once.
